# 交互设计场景

## 开工

1. `memory_search(scenario: "design", project: "<当前项目>")` 找相关记录
2. 看同层 `rules.md`：组件库版本、工具链、必须遵守的约束都在这
3. 先穷举状态，再画界面
4. 设计，然后把**结论**落成决策与认知

## 本场景的粒度

- **认知**：界面级。一个页面 / 一个流程一条，写结构、状态、跳转关系。
  典型：页面清单、状态枚举、数据来源、边界情况、组件库版本与可用的组件。
- **决策**：每个「用户能感知到的取舍」一条。
  典型：列表还是网格、错误提示放哪、删除要不要二次确认、空态展示什么。
- **品味**：视觉与文案偏好，**在有产物支撑时**才记。
  典型：偏好的信息密度、语气、动效克制程度。
- **纠错**：设计评审打回过才记。
- **工具**：出稿脚本、截图比对脚本——它们把「忘了某个状态」变成机器检查。

## 纪律

- **先穷举状态，再画界面**：加载 / 空 / 错误 / 无权限 / 超长文本，缺一不可。
- 每个交互决策都要能回答「用户这时候在想什么」。
- 不要只交"好看的图"，要交**状态与规则**。
- 交付物必须是能打开的 HTML，不是描述。用户点不到的东西等于没做。

## 硬规则通常长什么样

这个场景的硬规则集中在**工具链与版本**上，而且几乎都是「用户说过一次，之后不能再错」的类型：

- 组件库版本固定为哪个（哪个版本缺什么组件、缺的怎么兜底）
- 组件必须来自组件库，不许自己糊一个看起来像的
- 交付形态：可直接打开的 HTML，含交互与各状态

这类约束用 `doc_write` 写进本层 `rules.md`。**它们是最值钱的一类记忆**——因为它们一旦写错，会连续错很多稿。

## 典型纠错

- 只设计 happy path，漏掉空态和错误态
- 交互写在图里、规则留在脑子里，实现方无从判断
- 用视觉偏好冒充决策（"这个好看"不是理由）
- 用了错误的组件库版本，返工五轮（典型「该问没问」）

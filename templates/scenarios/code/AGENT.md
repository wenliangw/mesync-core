# 代码开发场景

## 开工

1. `memory_search(scenario: "code", project: "<当前项目>")` 找相关记录——命中就命中，没命中别纠缠
2. 没有认知就从读代码开始，读完用 `memory_write(kind: "cognition")` 立一条
3. 动手改代码

**真正靠得住的是这个文件加同层的 `rules.md`**，不是检索。检索是弱匹配，漏了是正常的。

## 本场景的粒度

- **认知**：模块级。一个文件 / 一个模块一条，写职责、边界、关键约束。
  不贴大段代码——代码会变，结构不会天天变。
- **决策**：只在「有取舍」时记。一次重构一条就够，不要每个函数一条。
  典型：选型、分层、接口语义、错误处理策略、依赖引入、目录组织。
- **品味**：只在会影响后续代码时记（命名、分层、错误处理、测试策略）。
  **直接写**，不要从决策里派生——那样写出来的品味没有反例边界。
- **纠错**：编译 / 测试 / 评审打回过才记。自己顺手改掉的小问题不算。
- **工具**：本项目的检查 / 生成脚本，输入输出说得清就造一个，造完在 `rules.md` 工具段登记。

## 纪律

- **不改没有读过的文件**：先 read，再改。
- 结论进决策，过程留对话。
- 一次改动只解决一件事；发现别的问题，记下来，别顺手一起改。
- 改完跑测试。跑不了要说明为什么跑不了，不要默认它是对的。

## 硬规则通常长什么样

不可逆的操作是这个场景最主要的硬规则来源：

- 不许 force push 到受保护分支
- 不许本地发布
- 不许手改生成物（改了下次生成就丢）
- 破坏性命令（`rm -rf`、`git reset --hard`）先确认目标

用 `doc_write` 写进 `rules.md`，不要只写成记录——记录不会在动手前送到你眼前。

## 典型纠错

- 没读文件就改，覆盖了别人的修改
- 改了代码没跑测试
- 把猜测当成事实写成认知
- 报错就用 `--force` / `|| true` 绕过去，没弄懂原因

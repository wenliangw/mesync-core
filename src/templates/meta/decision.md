## 决策：为什么这么定

决策是唯一**必须携带原因**的记忆。

判断标准只有一句：**要推翻它，需不需要先知道它为什么这么定？**
需要 → 决策。不需要 → 认知。

写不出原因，它就不是决策，只是一条事实或者一个偏好。

### 原因只有三种

| 类型 | 长什么样 | 怎么写 |
|---|---|---|
| **取舍** | 有别的方案，选了其中一个 | 写被放弃的方案 + 为什么不用 |
| **判定** | 原来的做法错了，改成现在这样 | 写违反了哪条 + 怎么防它再发生 |
| **外部约束** | 没得选（平台限制、别人的要求、合规） | **老实写「没得选」，不要编放弃项** |

最后一种最容易写歪。外部约束本来就没有放弃项，硬编一条「我们也考虑过另一个方案」是假的，会让后来的人以为这里有选择余地。

### 比放弃项更耐用的一句：什么情况下该重新考虑

「当时为什么选它」会过期——条件一变，理由就不成立了。

「什么情况下该重新考虑」不会过期，它同时告诉你**什么时候这条决策该被推翻**。

```
重新考虑的条件：如果组件库要求浏览器基线降到 IE，这个方案就不能用了。
```

写得出这一句，说明你真的想清楚了这个选择的边界。

### 会反复执行 → 变成硬规则

一条决策如果**以后每次都要照着做，而且不需要再解释为什么**，就用 `doc_write` 在**同层的 `rules.md` 里加一条硬规则**。

判据是两句话同时成立：

- 会反复执行
- 不需要再解释（解释已经让人接受了，下次只要执行）

这跟「重复几次」无关。一次就够——只要它显然会反复发生。

写进 `rules.md` 之后，决策正文**不要删**。规则是「做什么」，决策是「为什么」；规则会被违反，那时候需要知道为什么。

### 改主意了怎么办

**追加一条新的，指向旧的，不改旧正文。**

记忆是历史。把旧决策改写成新样子，等于抹掉了「我们曾经这么想过」——而那正是下次判断「这次的变化是不是又回到老路」的唯一依据。

新的那条要写清：什么变了、为什么之前那套不成立了。

### 不要写成流水账

决策记的是**判断题**，不是**过程**。

```
❌ 先试了 A，报错，然后试了 B，还是不行，最后改成 C
✅ 选 C：A 和 B 都要求同步阻塞，而这条路径不能被阻塞
```

过程留在 `path_record` 的路径里就够了，决策正文只留结论与理由。

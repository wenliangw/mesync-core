## 品味：用户认可过的做法

品味是「用户喜欢什么、希望我怎么做」，而且这个偏好**来自用户对某个产物的认可**。

它和决策的分工：决策回答「为什么这么定」，品味回答「下次默认怎么来」。

### 第一个问题：它会改变我下次的默认做法吗

不会 → **不记**。那只是这次的任务约束（「这次先不用测试」不是品味）。

会 → 继续问下面几个问题。

这一条能挡掉大部分不该记的东西。任务约束记成品味，会让 Agent 下次在不该套用的地方套用。

### 结论还是倾向

| | 特征 | 怎么写 |
|---|---|---|
| **结论** | 用户明确说过，边界清楚 | 对象 / 方向 / 理由 / 边界 |
| **倾向** | 我从几次认可里归纳的 | 方向 + **反例边界** |

倾向必须写反例边界，否则会被过度泛化。

```
❌ 用户喜欢简洁的代码
✅ 用户喜欢简洁的代码（倾向）；但错误处理里宁可啰嗦地把失败路径写全，不要为了简洁省略
```

没有反例的倾向，迟早会在不该用它的地方被用。

### 边界是谁定的，必须标

| 来源 | 怎么标 |
|---|---|
| 用户说的 | 「用户说的」 |
| 我推断的 | 「推断 · 待确认」 |

混在一起写的后果：下次无法判断哪条可以信、哪条需要再确认一次。

### 留一个产物指针

品味来自对某个产物的认可，那就把这个产物指出来：

**提交号 > 文件路径 > 文字描述**（越靠前越耐用）

打不开的指针等于没留。三个月后一句「上次那个按钮改过的样式」，谁也找不到。

### 如果它长出了硬规则

先怀疑它其实是决策。

品味是「倾向」，硬规则是「边界」。一条品味如果必须靠「不许」才能表达，那它约束的是行为而不是喜好——那是决策。

例外：用户明确说的偏好可以同时是硬规则（「我不接受纯黑背景」）。这时候标清来源是「用户说的」。

### 不记什么

- 一次的让步（「这次先用这个色」）
- 用户没说、我自己揣摩的审美
- 任何我没法说清「什么情况下不适用」的偏好

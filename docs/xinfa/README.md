# 元心法总纲

> 给人和 Agent 都能读。人是索引（五块各是什么、怎么流动、有哪些规则），Agent 按需读。
> 判据不在这里，在 `chain-judge.md`——这里只解释「为什么」和「怎么组织」。
>
> 常驻的只有 `chain.md`（586 字符）。这一份不进注入。

五块心法，覆盖一条经验的完整生命周期：

| 心法 | 是什么 | 判断含量 |
|---|---|---|
| **认知** | 事实（含硬边界） | 无判断 |
| **决策** | 为什么这样定 | 判断与理由 |
| **品味** | 判对了、用户认可 | 被认可的判断 |
| **纠错** | 判错了、有代价 | 被否定的判断 |
| **工具** | 不用再判，直接做 | 判断被省掉 |

事实 → 选择 → 认可 → 否定 → 固化。再多就是重复，再少就漏一环。

## 一条经验该记成哪一块

**判据只有一处：`chain-judge.md` 的 Q 链。** 这里不重复写——同一个判据写两遍，早晚会漂移（改一处忘一处）。

这里只解释**为什么是这个顺序**，这是链本身不会告诉你的：

- **「指向未来」在最前**：未来归调度，不归记忆。先挡住这一类，后面的问题才有意义。
- **「评价产物」在「要动手」之前**：品味和纠错来自**对产物的评价**，不来自动作本身。顺序反了会把「用户喜欢这么写」误记成工具。
- **「工具」挂在「要动手」下面**：工具只在你要做动作时才出现；不动手时不会缺工具，所以它不该挡在更前面。
- **「决策 / 认知」在最后**：它们之间的差别（要不要先知道原因）只有在前面都排除之后才有意义。

## 规则：挂在条目上的行为约束

规则不是第六块，也不是能自己站立的条目——它是**附着物**。
每条规则都属于一个母条目（认知 / 决策 / 品味 / 纠错 / 工具），并且要能回答「你为什么立这条」。

它解决的是这样一个问题：一条边界脱离它约束的东西，就没有意义。
「禁止本地 npm publish」不是一条通用事实，它只对「发布行为」有意义；离开发布流程，它什么都不是。

### 阶梯

```
判断  →  规则  →  工具
（要理解才能用）   （看到就遵守）   （机器执行）
```

一条品味 / 纠错 / 决策，稳定到「不需要再判断，照做就行」，它就该长出规则；
规则再稳定到「能机械判断」，它就该变成工具。**规则是沉淀的中间态。**

### 硬与软

| | 违反之后 | 例子 |
|---|---|---|
| **软规则** | 我说一句「我改」就能解决 | 别用三目运算符 |
| **硬规则（边界）** | 不可逆：东西改不回来，或者信任收不回来 | 禁止本地 `npm publish`、禁止 force push 到主分支 |

判据还是那句：**违反之后，我说一句「我改」能不能解决？**

分布上有规律：**硬规则多来自决策和工具**——不可逆的后果都出在动作上；
**软规则多来自品味和纠错**——审美和教训，违反了可以改回来。

所以一条品味如果长出硬规则，通常说明它其实不是品味，是决策：它有实实在在的代价。

### 铁律

> **规则不许凭空存在，必须能指向它的母条目。**

外部硬约束（许可证不能是 GPL、平台要求兼容 iOS 15）也要有母条目：先记成一条认知，再挂规则。
这样每条规则都能解释自己为什么存在，不至于变成一堆来源不明的教条。

### 一条规则的形状

一项行为，四行写完：

```
行为：改文件之前先读完它
硬度：hard
判据：看有没有 read 就直接 edit
来源：corrections/unread-edit
```

**「判据」是写给人（Agent）看的描述，不是可执行代码。**
当某条判据稳定到能机械判断（一条 grep、一个正则就够），它就该沉淀成工具——
那时规则退到工具的说明里，不再需要 Agent 每次读一遍。

### 目录：条目即文件夹

规则跟着母条目走，母条目搬家时规则不会掉队：

```
<块>/<条目>/
  本体            # taste.md / correction.md / decision.json / README.md / 认知节点
  rules/
    一项行为.md    # 一个文件 = 一项行为
```

### 加载

- **软规则**随母条目加载（读到那条品味，就拿到它的软规则）
- **硬规则**必须比检索更早生效——进常驻清单，一行一条

而且**硬规则应该很少**。常驻清单涨到几十行，说明分级判错了：那些其实是软约束，
或者它们该变成工具了——**让机器拒绝，比让 Agent 记住可靠**。

## 五块之间怎么流动：判断含量的升降

五块是按**判断含量**排的（无判断 → 有理由 → 被认可 → 被否定 → 判断被省掉）。
所以它们之间的流动只有两种方向，加上一种横向的换块：

- **沉淀**：判断变成确定性（判断被省掉）
- **上浮**：确定性被破坏，判断回来
- **换块**：一条判断被验证后，落到正面或负面的那一块

不管管这三条，会出现两种坏结果：一条洞见被分散记在五块里互相打架；
或者一条硬边界永远以「品味」的形态存着，被当成可以商量的偏好。

### 沉淀：判断变成机制

| 从 → 到 | 判据（问这一句） | 例 |
|---|---|---|
| 决策 → 认知 | **原因是不是已经不需要被知道了？**（新来的人不问为什么，而且原因已写在别处） | 「用 pnpm」当初是决策；现在团队只当事实 |
| 品味 → 硬边界 | **违反一次的后果可不可逆？** | 「别用三目运算符」是品味；「禁止手动 npm publish」是硬边界 |
| 纠错 → 工具 | **同一个错是不是犯了第二次？** | 记过「提交前要跑测试」还是忘 → 做成提交钩子 |
| 任一块 → 工具 | **输入输出能说清、中间没有「看情况」？** | 每次都要手工做一遍的检查 → 脚本 |

前两条都在**抽掉理由**，所以有一条铁律：

> **沉淀不是遗忘。降级之前，先确认理由在别处存在**（文档、规范、团队共识，或者这条决策本身还留着）。

理由没地方去的，不要沉淀——那不是稳定，是失忆。

### 上浮：确定性被破坏

| 从 → 到 | 判据 | 动作 |
|---|---|---|
| 认知 → 决策 | **复验不通过，而且修复方式不唯一** | 先追加决策（改成什么），再更新认知 |
| 工具 → 纠错 | **工具出错，或环境让它不再成立** | 先查是不是「判断塞进了工具」，再改工具 |
| 硬边界被违反 | **越界真的发生了** | 决策记怎么补，纠错记为什么没拦住 |

最后一条要特别注意：**硬边界被违反，通常不是内容记漏了，是它根本没被加载。**
要修的是加载方式，不是把边界再写一遍、写得更醒目一点。

### 换块：验证结果落到哪

| 从 → 到 | 判据 |
|---|---|
| 决策 → 品味 | 用户认可的是**这个做法**，不只是这次结果 |
| 决策 → 纠错 | 按它做了，结果错了，而且有代价 |
| 纠错 → 品味 | 判错之后给出了对的做法，而且这个做法被认可 |

「决策被证伪」要**同时**落两块：新决策记「改成什么」，纠错记「我为什么判断错」。
分开记才有用，因为检索时机不同——决策在下次做同类决定时被想起，纠错在动手之前被想起。

### 一条不该跨的线

**品味不要升级成决策。** 品味没有放弃项，硬升就得编一个——那就是「编出来的放弃项」，比不记更坏。

反过来，认知升成决策有明确判据（要推翻它需不需要先知道原因），这条写在认知心法里。

### 一条总的原则

**记忆里没有「删除」，只有「换一种存法」。**

降级标「已沉淀」，推翻标「已被取代」，根治标「已根治」——旧条目都留着。
因为它们的价值不是「现在还对不对」，而是**能解释现在为什么是这样**。

## 五块共用的写法骨架

每份心法都回答同样四件事：

1. **怎么认出来**——什么迹象说明这里有该记的东西
2. **值不值得记**——影响后续行为的才记
3. **怎么写才用得上下次**——写给「三个月后检索到它的自己」看
4. **什么时候该改**——被否定、被推翻、过期之后怎么办

## 素材与产物：范例不单独成块

「范例」不是第五块。一个范例是**做完并被用户认可的产物**，它的价值已经在记忆里了：

- 认可的那部分 → **品味**
- 失败的那部分 → **纠错**

但两者都要留一个**指向产物的位置**（文件路径 / 提交号 / 设计稿），因为「为什么算好」脱离了实例就说不准。

## 触发时机：三种时机，不是一套检索逻辑

| | 什么时候出现在眼前 | 靠什么 |
|---|---|---|
| **认知 / 决策 / 品味 / 纠错** | 想起某件事时 | 按主题检索（弱匹配，够用即可） |
| **工具** | 动手之前 | **M1 交付清单**，不靠「记得去找」 |
| **未来**（承诺 / 待办 / 还没定） | 不出现 | 不入这套模型，归调度 |

这里有一条从「纪律」变成「机制」的迁移，值得单独说：

- **旧做法**：嘱咐 Agent「动手前记得找工具」。
- **为什么不行**：想不起来的时候，正是最需要它的时候。嘱咐在最关键的时刻失效。
- **现在**：M1 把工具清单送到眼前。**不靠纪律，靠交付。**

认知 / 决策 / 品味 / 纠错为什么不也这样？因为它们会涨到几千条，全部常驻就不省了。
它们只能按需检索，而检索是弱匹配——这是当前已知的能力上限（见 [architecture.md](architecture.md) 第十一节）。

未完成事项不入这套模型的原因不同：它们**按时间**触发，属于调度。记录权跟判断权走。

# 链 · 维护规则（修链时才读）

> 平时不读。两类时刻才用：**用户否定后要修链**，或**怀疑链本身有问题**。

## 确定度标记

标记属于「一次行走」，不属于链本身——链上写的是判据，同一个节点这次可能硬判、下次可能勉强判。
所以标记记在路径里，不写进节点定义。

```
!   硬判：有明确依据（用户说过、代码里读到、判据本身无歧义）
?   勉强判：靠猜，或者两个分支都说得通
```

一次行走的路径记录形如：`Q2! → C1! → C2? → C4!`

| 本次路径 | 用户认可产物后 |
|---|---|
| 全是 `!` | **路径被确认**，算一次证据 |
| 含 `?` | 只确认了产物；路径不积累证据（那是幸运路径） |

副产品：某个节点长期出现 `?` → 说明**判据本身不清**，该改判据，而不是改答案。

## 掉落与修正

```
掉落      任何 else 走散文，并记一句「我凭什么这么判」
加分支    同一点掉落两次才允许；分支必须引用那两次掉落
定位      用户指出问题 → 重走本次路径，第一个与反馈冲突的节点 = 出错点
重建      出错点及其全部下游重建（上游假设仍然有效）
记录      fix: <日期> 节点=<id> 类型=判错|例外 证据="<用户原话>" 重建=<下游节点>
边界      「只追加不改写」只约束记忆，不约束本链——记忆是历史，链是当前方法
```

## 节点状态

决定它算骨架还是枝节，**不靠权限划分，靠证据量**：

| 状态 | 判据 | 处理 |
|---|---|---|
| 稳定 | 一直被走 | 就是骨架 |
| 新生 | 刚因掉落而加 | 观察，别当铁律 |
| 闲置 | 很久没被走过 | 降级，不删除（它解释过曾经的判断方式） |

## 可读与可查

链不给人看，所以**不必可读**；但每次修正必须留证据引用（哪次否定、用户原话、出错节点、重建了哪些下游），所以**必须可查**。

这两件事不能混：「不给日常阅读」是效率选择，「不可追溯」是隐患。

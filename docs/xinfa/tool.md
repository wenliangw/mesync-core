# 元心法 · 工具

工具是五块里唯一会**动手**的一块。
另外四块沉淀理解，工具沉淀**已经不需要再判断的那一步**。

---

## 一、什么时候该造

> **你能把这一步的输入、输出说清，且中间没有「看情况」——它就该凝固成工具。**

出现下面任一情况，就别造：

- 你需要先问「这回算哪种情况」——那说明还在判断
- 只做一次，以后不会再遇到
- 输入输出说不清（你自己都不知道「做对了」长什么样）

**次数不是理由。** 一个判断稳定的步骤自然会重复，但重复本身不构成造工具的理由。

一句话：**工具承担确定，心法承担判断。**

工具里一旦出现「如果……那就……」的业务分支，说明你把判断塞进了工具。这是最容易犯的错——它当下很好用，代价是以后每次都要验证这个判断还成不成立。

---

## 二、造的形状

你没有手艺记忆。下次拿起这个工具的是另一个「你」，它手里只有工具本身和它旁边的说明。

所以好工具只有一条标准：**不认识它的人也能一次用对。**

### 工具旁边必须有说明，六项缺一不可

1. **做什么**——一句话，动词开头
2. **什么时候用 / 什么时候不要用**——不用它，比用错它常见得多
3. **怎么调**——参数、默认值、例子
4. **会改什么**——写文件？改状态？发网络请求？**副作用必须写明**
5. **怎么看结果**——输出什么、怎么判断成功
6. **失败了怎么办**——下一步做什么，不是抛一段栈

### 代码本身

1. **一个工具做一件事**。名字说清它做什么，而不是它属于哪个模块
2. **能反复跑**：同样输入得到同样结果，跑两次不弄坏东西。做不到就写「只能跑一次」
3. **报告实际做了什么**，不只是退出码。最危险的失败是「看起来成功了，其实什么都没做」——**静默成功比报错害人**，因为报错你会去查，静默成功你会直接往下走
4. **失败时给下一步**，不是抛栈
5. **不猜**：缺参数就报错，不要用默认值蒙一个。蒙错的默认值比报错贵得多
6. **依赖最少**：只依赖这个场景保证存在的环境

---

## 三、怎么用

**动手之前先找，别重造。** 造之前的第一个动作，是问：这个场景里是不是已经有一个了。

- 用之前读说明，**不要猜参数**
- 它跑出来的东西是**证据**：可以记成认知，也可以支撑一条决策
- 它失败了，先怀疑自己的用法，再怀疑工具本身
- **不要给它加临时参数来「灵活处理」**——那是在工具里塞判断，塞进去的每一次都会留在那

---

## 四、怎么迭代

工具会腐烂，而且主要是**被绕过**杀死的：

> 工具报错 → 你临时手工做了一遍 → 下次还手工做 → 工具就死了。

所以要**修，不要绕**。绕过一次，工具就少一个用户；绕过三次，它就成了没人敢动也没人用的摆设。

三种该做的维护：

- **修**：报错、结果不对 → 改工具，而不是改用法
- **同步说明**：改了实现不更新说明，**比没有说明更危险**——没有说明时会去读代码，说明错了就不读了
- **退役**：如果它本来就不该存在（准入判断错了），明确标废弃。别让它半死不活地躺着继续误导人

**什么时候该退役**：环境变了、出现了更好的工具、它守护的那个问题已经不存在了。

## 附：这块能长出什么规则

工具自带**使用规则**，而且通常是 hard——工具的误用往往不可逆（跑了不该跑的脚本、在错误的分支上发布）。

例子：「只能在主分支上跑」「跑之前必须确认备份存在」。

这类规则最好直接写进工具本身（启动时自查），而不是留在说明里等人读。
**能进工具的规则，就别留在纸面上。**

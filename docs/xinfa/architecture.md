# mesync 架构

> 这张图是为了暴露分歧用的。你指着任何一处说「这里不对」，比继续讨论更有效。
> **本文描述现状，不描述愿景。** 还没实现的东西会在原处标明「未实现」。
> 未决的设计（多事实、联想）不在这里，见 `../未决设计.md`。

## 一、全景：三层东西，一场行走

```
常驻层（每轮都在，约 690 字符）
  一条链：M0 → M1 → M2 → M3 → M4 → M5
  任何节点答不出来 → 查 / 问用户 / 自己判
     │                    │                     │
材料层（固定路径）      工具层（脚本）         记录层（散文）
  该层 AGENT.md         publish.sh             决策 / 品味
  meta/*.md             ...                    纠错 / 认知
  chain-judge.md        工具之间可以互调        工具说明
  chain-rules.md        这就是「网」，不需要     ── 档案：只被查询
                        我们建图                ── 不进交付、不参与行走
     ▲                                             │
     └──────── 固化（记录 → 检查 / AGENT.md）────────┘
```

**关键：只有链参与行走。** 材料、工具、记录都没有「起点」，它们只在被链调到的那一刻出现。

**这一版最要紧的一条**：记录是**档案**，不是主路径。它只在被追问原因时才读。让 Agent「知道该怎么做」的责任，由三样更可靠的东西承担——机器检查（不会忘记）、项目里就地的东西（改到那儿必然看见）、该层 `AGENT.md`（每任务必到）。

**提问是这条链上唯一伸向外部的地方。** 它不属于任何节点——任何节点答不出来时都可能暂停下来问。

## 二、两条轴：先定位，再工序

任务是层层收窄的（场景 → 项目 → 这次要做什么），工序是固定顺序的（交付材料 → 做 → 评价 → 沉淀）。两者正交，必须分开。

```
     ┌──── 定位轴（纵向，逐层收窄，可停在任意层）───────────┐
     │                                                     │
     │  ↑ 往上：场景级（所有项目通用）← 跨项目偏好的落点      │
     │  │                                                  │
 M0  场景 ──→ 项目 ──→（模块，未实现）──→ 这次要做什么       │
     code       A                                          │
     │                                                     │
     │  往下每层交付该层 AGENT.md；选哪一层是「列目录 + 读你的话」│
     │  —— 机械动作，不是检索                                │
     └─────────────────────────────────────────────────────┘
                              │ 任务不再有歧义
                              ▼
     ┌──── 工序轴（横向，固定顺序）──────────────────────────┐
     │  M1 交付 AGENT.md → M2 做 → M3 评价 → M4 沉淀 → M5   │
     └─────────────────────────────────────────────────────┘
```

定位轴回答「我在哪里」，工序轴回答「我干到哪一步」。

### 定位轴的终止条件不是层数

停止条件是：**任务不再有歧义**。

- 「怎么跑起来这个项目」→ 到项目层就够
- 「parser 模块为什么要这么切」→ 需要模块层（**未实现**，现在只能靠项目层 + 直接读代码）

定位深度由任务决定，不由目录深度决定。**只下沉够用的层数**，这就是省 token 的地方。

### 往上的那一层：场景级

定位轴看似只能往下，但记录有**两个落点**，一个往下、一个往上：

```
scenarios/code/records/taste/             ← 场景级：所有 code 项目都适用
scenarios/code/features/A/records/taste/  ← 项目级：只对 A 适用
```

判据只有一句：**内容里出不出现具体项目名。**

- 「以后所有项目都用 pnpm，不用 npm」→ 没出现项目名 → **场景级**
- 「A 项目的测试要带 `--filter`」→ 出现了 → **项目级**

没有这个落点，「以后都用 pnpm」这类话就没有地方存——它不属于任何一个项目。

### 层文件：目录就是层级

每层的形状固定，只有两样：**一个交付文件 + 一个档案目录**。

```
scenarios/code/
  AGENT.md                     ← 场景层交付（做法 + 必须遵守的 + 工具）
  records/<kind>/*.md          ← 场景级档案
  features/A/
    AGENT.md                   ← 项目层交付
    records/<kind>/*.md        ← 项目级档案
    modules/parser/            ← 模块层（未实现，不要预建）
```

层级由目录承载，不需要 schema。每下沉一层只多交付**一份**增量材料，不是把所有相关记忆都灌进去。

**为什么每层只有一个交付文件**：交付文件是每任务必到的东西，它一旦变大，每次任务都要付这个成本。两个交付文件意味着「同一件事该写哪」有歧义，最后两边都写，成本翻倍。

### 定位过程中的选择不需要检索

- 用户说了「A 项目」→ 直接就是答案
- 没说 → 列目录（`ls`，机械动作，不是语义检索）
- 列出来都不匹配 → 问一句，或猜最可能的

### 两条纪律

1. **最多两层**（场景 → 项目；模块层未实现）。再深要先证明「只靠这两层确实不够」，而不是先把目录铺开。
2. **允许回退**：在项目层发现「这其实是场景级的问题」→ 回上一层，跟 M3 否定回 M2 同理。

## 三、链的形状

**形状只有一处定义：`templates/mesync-use.md`（常驻）+ `chain-judge.md`（M4 交付）。** 这里不重复画第二份——同一个形状写两遍，改一处忘一处就会漂移。

这里只说几件**图上看不出来**的事：

1. **M0 有两个出口**——「产出」走工序轴，「回答」跳过工序轴。少了这个出口，问答轮无处可走，Agent 只能自己判断要不要走链，那就又回到「依赖它自己识别」。
2. **M1 不是「找」，是「交付」**——材料送到眼前才算走完。只嘱咐「记得找工具」等于没做，因为想不起来的时候正是最需要它的时候。
3. **提问不在流程里**——它挂在「答不出来」这件事上，对任何节点开放，形式是「暂停等答案」而不是新节点。做成固定阶段就会退化成仪式，详见 §五。
4. **M4 才读判断分支**——Q 链不在常驻里。触发它的是节点（走到 M4），不是判据本身。这是「判据入口」和「判据细节」的分离。
5. **M4 的第一问不是「记哪一块」**——是「它有没有确定的读取路径」。分类在出口之后，详见 §四。

### M1 交付什么（具体）

**该层的 `AGENT.md`，一份。** 同时装三样：

```
① 这个作用域怎么做 —— 开工步骤、产物形态、默认做法
   1. 改代码前先 pnpm test
   2. 产物落 dist/，不要手改（改了下次构建会被覆盖）
   → 涨到几十行说明在把「流程」当「事实」写

② 必须遵守的 —— 违反后果不可逆的那些
   出稿前 grep 一遍 import，确认组件库版本是 v3.2
     来源：records/decision/组件版本.md
   禁止 force push 到 main（来源：records/decision/分支保护.md）
   → 每条带来源：规则是「做什么」，来源是「为什么」

③ 工具 —— 这个作用域里已经有什么
   pnpm build      构建，产物在 dist/
   scripts/copy-assets.mjs   拷贝模板，构建时自动跑
   → 只写这周真用过的，不抄 package.json 全部脚本
```

平台自带的（bash / read / edit / grep）不进这里——它们本来就在 context 里。

**「找」只发生在一处**：选中某一行之后，才去读它的详细说明。都没有，才考虑造工具。

### 为什么不交付记录

记录的数量**不可控**，而检索质量随条数下降。把记录放进候选集，等于把「能不能用上」交给一次不确定的命中。

实测：记忆从 225 条涨到 18 000 条，注入只从 1507 字符涨到 1547 字符——因为记忆正文一律不进注入。但 `scenario_load` 的交付会随该层内容线性涨：3 条硬规则 1994 字符、20 条 2905、60 条 5065（约 54 字符/条）。

**结论：膨胀不会消失，只会搬家。** 所以每任务必到的那条路径必须是有形状的（一个文件、有参考线），而不能是「读一批记录」。

### 交付文件有参考线，没有上限

超过约 **2000 字符**时，`doc_write` **仍然写入成功**，只追加一段提醒：按长度列出最长的三块，给三个自问（有两条在说同一件事吗 / 最长那条能不能一句话说完 / 有没有一条该变成检查或注释）。

**它是铃，不是闸门。**

- 闸门是用机制替 Agent 做判断，而「该不该压缩」是判断
- 铃只负责察觉，每次越线都响，并且给具体对象——抽象的数字会被忽略，「这三块最长」不会
- 允许不整理，下次再超线还会问一次

超限的真实后果不是被拒，而是**每轮注入变胖**——因为这份文件每任务必到。

### 生长是改写，不是追加

允许无限追加的系统永远不会泛化。所以交付文件的成长方式是**压缩**：把两条并成一条、把「这个项目」写成更一般的说法、把一条变成检查或代码注释从文件里移出去。

参考线就是把「该改写了」这个时刻送到眼前的机制。

## 四、出口判据与五个叶子

**定义只有一处：`chain-judge.md`，走到 M4 才读。** 这里只说结构。

### 先问出口

```
Q1 指向未来?           y→不记（归调度）
Q2 机器能检查?         y→写成检查（lint/测试/hook）
Q3 该生效处已有?       y→不记（那是重复）
Q4 每任务都要照做?     y→doc_write 进该层 AGENT.md
Q5 能靠已知关键词找到? y→记成五块之一
   否则                → 不记
```

三条读取路径的可靠度递减：机器检查（不会忘记）→ 项目就地（一定看见）→ 交付文件（每任务必到）→ 记录（只在被追问时读）。

**记录是最不可靠的一种归宿，所以它不该是默认选项。** 推论：大部分东西的正确答案是「不记」。

### 叶子不是标签，是交付点

Q5 为 y 时才用。五个叶子各自**指定一份材料**：

| 叶子 | 交付 | 写什么 |
|---|---|---|
| K 认知 | `meta/cognition.md` | 结构与约束 / 怎么验证还成立 / 来源 |
| D 决策 | `meta/decision.md` | 定了什么 / 为什么 / 何时该重考虑 |
| T 品味 | `meta/taste.md` | 对象 / 方向 / 理由 / 边界 / 产物指针 |
| C 纠错 | `meta/correction.md` | 症状 / 触发 / 检查 / 止损 |
| TL 工具 | `meta/tool.md` | 做什么 / 何时用 / 会改什么 / 失败怎么办 |

这不是「分类标签」，而是**走到叶子必然会拿到那份写法**。所以「该看哪份心法」这件事不需要判断——判断被节点替掉了。

**五份不合并**：它们按需读，合并只会让每次读变大。按需的东西多一个不多，必读的东西多一个才要命。

### else 出口是链的缺口，不是容错

任何节点答不出来就掉到散文心法，并记一句「我凭什么这么判」。

**掉落的记录就是链生长的原料**——同一个点掉两次，才允许给它加分支。

### 否定不等于「我错了」

| 原因 | 该记什么 | 例子 |
|---|---|---|
| **信息缺失**：用户事先没说过这个要求 | 认知 + 该层 `AGENT.md`（确立默认值） | 「第一次没说用 3.2，我用了 3.1」 |
| **判断失误**：依据本来就有，我没用好 | 纠错 | 「项目里明明写着 3.2，我读了却用 3.1」 |

判据一句话：**用户事先说过吗？** 说过 → 纠错；没说过 → 不是纠错，是该补的默认值。

分不清的后果很实际：把「需求没说清」全记成「我判断错了」，纠错块会被灌满，最后它的诊断价值就没了。

## 五、提问：随时可以停，但不是固定阶段

提问**不是链上的一个节点**。两个理由：

- **卡住的地方不可预测。** 有时读完需求就知道缺什么，有时要动手到一半才发现。
- **做成节点就会变成仪式。** 每轮走到那里，没东西问也走一遍；几十轮之后就没人真看了。

所以它挂在**「答不出来」**这件事上。

### 三种出口

```
① 能查到              → 查，查完继续（不算出口）
② 查不到，猜错要返工    → 停下来问用户，答案进临时区，回来从原节点继续
③ 其余                → 走散文心法自己判，并记「我凭什么这么判」← 这才是「掉落」
```

**② 是一条暂停，不是分支**：问完回到原来那个节点，链的形状不变。

### 判据

> **能查先查；查不到，且猜错要返工，才问。**

| 情况 | 动作 |
|---|---|
| 能自己查到的（读代码 / 读文档 / 列目录） | 先查，别问 |
| 查不到，但猜错了改起来便宜 | 猜，别问 |
| **查不到，且猜错要返工** | **问** |
| 用户已经说清了 | 不问 |

三条缺一条就别问。少了这条约束，Agent 会变成「问个不停的助手」——那是另一种失败。

### 该问的三类

1. **缺口的填充**：「v3.2 没有 A、B 组件，用什么替代？」
2. **冲突的裁决**：「这个要求和上次定的规范打架，保哪个？」
3. **范围的边界**：「改到只动这个稿子，还是所有同类稿子一起改？」

共同点：**答案会变成长期规则，猜错的代价是连续的。**

### 怎么问

```
❌ 一个一个问
   「用哪个组件库？」→ 答 →「哪个版本？」→ 答 →「缺的怎么办？」→ 答

✅ 一次问完，带建议答案
   有一处定不了：v3.2 缺 A、B 两个组件。
   我倾向「优先 3.2，缺的用 3.1 兜底」——这样对吗？
```

**带上我倾向的答案**，用户只需点头或否决；**说清为什么问**，用户才知道值不值得花时间。

### 答案先进临时区，不进记忆

```
问 → 临时区（标记：这次的做法）
      ↓
M3 认可成果 → 升格为正式记忆 / 该层 AGENT.md → 删除临时
M3 否定     → 丢弃                          → 删除临时
```

理由：我问出来的是「**这次**怎么做」，用户答的时候也是针对这次。只有成果被认可，才证明这个答案是对的。

反例很贵：把没验证的答案写成规则，下次会照一条错规则执行，而且它**看起来有依据**，比没有规则更难被发现。

### 两个例外

| 情况 | 处理 |
|---|---|
| 用户的**直接指令**（「以后都用 pnpm」） | 直接落盘——那是指令，不是我的推断 |
| 能查到的**客观事实**（package.json 里的版本） | 直接落盘——事实不需要用户验证 |

### 用户答得随意怎么办

用户回「随便」，不是给了答案，是**授权你决定**。此时应当自己拍板，并明确说出拍板结果——这样用户还能事后否决，而不是不知道你替他定了什么。

## 六、一次任务的实际行走

```
用户：把组件库升到 v3.4
   │
   ▼
M0  产出是代码 → 场景 code
   │
M1  scenario_load('code')
      场景层 AGENT.md（这次要改 import，看「必须遵守的」）
      项目层 AGENT.md：做法 + 「组件版本固定 v3.2，改 import 前先 grep」
      用量 1240 / 2000 字符
   │
M2  按交付里的做法：grep 全部 import → 改版本 → 跑测试
   │
M3  用户说「对」→ M4
   │
M4  有没有东西要留？
      Q1 不指向未来 ✓
      Q2 能不能变成检查？能 → 写成 CI 检查        ← 优先这条
         或者 Q4 每任务都要知道 → 改写项目层 AGENT.md 那一条（v3.2 → v3.4）
         或者 Q5 → 记一条决策（为什么固定版本）
   │
M5  path_record("M0!→M1!→M2!→M3!→M4!→D! 组件库升到 v3.4，版本检查变成 CI")
```

**注意 M4 的优先顺序**：这里首选「写成检查」而不是「记一条决策」。因为检查不会忘记，记录会被遗忘。

## 七、数量关系

| 东西 | 数量 | 有起点吗 | 每轮必到吗 |
|---|---|---|---|
| 链 | **1 条**（685 字符） | 有，M0 | **是** |
| 场景清单 | N 行（只名称 + 判据 + 产出） | 无 | 是 |
| 该层交付 `AGENT.md` | 每层 1 份 | 无 | 是（M1 交付） |
| 材料（五心法 / 判断分支 / 维护规则） | 固定 7 份 | 无 | 否，按需 |
| 临时答案 | 每次 0–3 条 | 无 | 否，落盘后即删 |
| 工具 | M 个 | 无 | 否，只在被调用时 |
| 记录 | K 条 | 无 | **否**，只在被查找/固化时 |

**注入不随记忆增长**：实测记忆 225 → 18 000 条，注入 1507 → 1547 字符。因为记录正文一律不进注入，覆盖度只报条数（最多 8 行）。

## 八、生长：一开始什么都没有

### 起点：有种子，没枝叶

**内置（不生长）**：常驻链（`mesync-use.md`）、判断分支、维护规则、五份心法、三个场景骨架（code / design / prd）

**空的（要生长）**：各层 `AGENT.md`、各层 `records/`、工具

### 顺序（每样的原料都是别的东西）

```
第一次干活什么都没
   → 只能探索（唯一允许「不按经验」的时刻）
   → 结果被认可
        ↓
   写记录 / 写该层 AGENT.md        ← 原料：这次发生了什么、怎么干成的
        ↓
   第二次同类任务：M1 直接交付       ← 不再探索（生长第一次生效）
        ↓
   同一决策第二次执行
        ↓
   写进该层 AGENT.md 的「必须遵守的」 ← 原料：这条会反复执行
        ↓
   同一动作第三次手做
        ↓
   固化成工具                       ← 原料：记录里的重复
        ↓
   AGENT.md 工具段出现那一行         ← 原料：工具真的存在了
```

**每一样都在它的原料出现之后才创建。** 没有一样提前建。

**最干净的原料来自提问**：用户亲口答过的，比猜出来的可靠得多。但问来的答案**也要等成果被认可才落盘**。

### 创建触发条件（防歪的全部内容）

| 东西 | 什么时候创建 | 不满足就 |
|---|---|---|
| 该层 `AGENT.md` | 这一层有「下次还会用到的干活方式」时 | 不建，不为每个项目预建目录 |
| 记录 | 走完 Q 链落到某个叶子 | 不写 |
| `AGENT.md` 的「必须遵守的」 | 同一条决策**第二次**要执行时 | 不写（一次不构成理由） |
| 工具 | 同一动作**第三次**手做时 | 不写 |
| 工具段那一行 | 工具已经存在之后 | 不写（否则是空头支票） |
| 链分支 | 同一个 `else` 出口**第二次**被走过 | 不加 |
| 检查 / hook | 一条纠错重复出现时 | 不写，留在记录里 |

### 一条防线：失败的探索不进交付文件

M3 走否定分支时，**交付文件不写**，只写一条纠错。

因为交付文件会被下次直接当作「怎么干活」来执行，写进去的必须是被认可过的。**坏经验只能进纠错，不能进 `AGENT.md`。**

### 生长不是单独的机制

它是 **M4「这次留下了什么」的副作用**。链走完，该写的写了，目录自然长出来——没有链之外的自举机制，也没有初始化步骤。

触发条件表管的不是「怎么长」，而是「什么时候**不该**长」，防止一开始就把目录铺满空文件。

## 九、十六条判断（当前状态）

- ✓ **1. 链只有一条**，场景只是 M0 的一个分支，不是多条链。（已认可）
- ✓ **2. 场景下做过的任务不是链**，是记录；不参与行走，只被查找或被固化。（已认可）
- ✓ **3. 复用靠工具被调用**，不靠链之间共享节点（所以不需要 `ref` 边）。（已认可）
- 4. **两条轴正交**：定位轴（纵向收窄）+ 工序轴（横向固定）。
- 5. **链不存状态**，每轮从 M0 重走；常驻 685 字符，重走成本可忽略。
- 6. **材料由节点交付**，路径写死，不靠 Agent 检索决定读哪份。
- 7. **查找只发生在两处**：追溯（`memory_search`，已知有这么一条）与固化检测（M4 问「记过同一件事吗」）。**两处都不是召回**——数量不可控时召回不可靠。
- 8. **「网」是工具之间的调用关系**，天然存在，不需要我们建图。
- 9. **唯一的向上流动是：记录 → 固化 → 检查 / 工具**；链本身不生长（除加分支）。
- 10. **层级由目录承载**，现在两层（场景 → 项目），任务不再有歧义就停止下沉。
- 11. **M0 有两个出口**：产出（走工序轴）和回答（跳过工序轴）。
- 12. **记录有两个落点**：场景级（跨项目通用）和项目级（带项目名），判据是有没有出现项目名。
- 13. **链按「读的时机」拆三份**：常驻段（685 字符）、Q 段等 M4 才读、维护规则等修链才读。省 token 的不是「链」这个形式，是「只常驻必须常驻的」这个决定。
- 14. **提问不在流程里**：挂在「答不出来」上，任何节点都可能暂停问用户。
- 15. **否定不等于我错了**：用户事先没说过 → 补默认值（认知 + `AGENT.md`）；说过 → 纠错。
- 16. **问来的答案先进临时区**：成果被认可才升格落盘，否定就丢弃。

## 十、走查：真实场景压出来的漏洞

拿真实场景把这张图走了一遍（修 bug、设计稿输出、跨项目偏好、纯问答、「继续」、多任务并行），压出四个漏洞，**已修**：

| # | 漏洞 | 症状 | 修法 | 改在哪 |
|---|---|---|---|---|
| 1 | M0 缺「回答」出口 | 「TS 的 satisfies 和 as 有啥区别」判不出场景，会逼 Agent 自己判断「这轮要不要走链」 | M0 改成二分支：产出 / 回答 | `mesync-use.md` M0 |
| 2 | 定位轴只能往下 | 「以后所有项目都用 pnpm」不属于任何项目，无处落 | 记录加场景级落点，判据是内容里有没有项目名 | 本文 §二 |
| 3 | 一次否定可能落三块 | 「这个配色不好，我不喜欢冷的」= 品味 + 纠错 + 决策，而一次只落一条 | 按出口优先级选一条，其余留路径里 | `chain-judge.md` §六 |

### 真实事故：组件版本 v3.1 → v3.2

> 来自旧 mesync 的真实案例，用来检验新架构是否真的挡得住。

**经过**：用户只说「做个设计稿」，Agent 用了 v3.1。用户要求改成 v3.2，Agent 改了 5 轮才对，每轮都产生了决策。用户以为记了品味和决策，下次会自动用 v3.2——**结果下次还是 v3.1**。

**旧架构为什么挡不住**：决策和品味都记了，但它们躺在库里等**检索命中**。记下来 ≠ 会被用到，中间隔着一个不确定的检索。

**新架构挡在哪**：

| 时点 | 新架构会做什么 | 结果 |
|---|---|---|
| 第 1 次出稿 | 查不到版本 → 停下来问「用哪个版本？」 | **可能一开始就对** |
| 第 1 次被否定 | 判定依据（用户事先没说过）→ 写进该层 `AGENT.md` 的「必须遵守的」 | 进入交付区，不进入档案 |
| 第 2–5 轮 | 噪音决策照样产生 | **淹不掉那条约束**，因为它不在同一个池子里 |
| 第 3 次新稿子 | `M1` 交付的 `AGENT.md` 里就有这条 | **确定性看见，不再靠命中** |

**关键差别一句话**：该被交付的东西，不能放进需要命中才能被看见的地方。

**这个案例还压出两个漏洞**（已修）：

- 用户事先没说过版本 → 这不是「我判断错了」，把「信息缺失」记成纠错会污染纠错块（见 §四）
- v3.2 未必有 v3.1 的全部组件 → 缺口的填充必须问，不能默认「新版就全」（见 §五）

**结论**：新架构下这个事故变成「第 1 次可能错，第 2 次必对」。这条标准由 M1 交付保证，不由检索命中保证。

四个**可接受的限制**（不修，写下来免得反复讨论）：

| # | 限制 | 为什么可接受 |
|---|---|---|
| 5 | 新会话第一句说「继续」无法理解 | 没有上下文就没有「继续」的对象，本来无解 |
| 6 | 多个任务并行要串行化 | 「任何时刻只有一个当前节点」是刻意施加的约束 |
| 7 | M0 判错要回 M0 重走 | 允许回退，跟 M3 否定回 M2 同理 |
| 8 | 大任务按轮走，M4 每轮都问「留下什么」 | 允许答「没有」，一句话通过，成本可忽略 |

## 十一、我最不确定的地方

- **参考线 2000 字符是推的，不是测的**。它来自「3 条硬规则 1994 字符」这一条实测基线，没有真实使用数据支撑。两层合计约 1400 token/任务，可能仍然偏重。
- **「猜错要返工」事前判断不准**：这是事后才知道的事。高估了会问太多，低估了会重蹈 v3.2 那 5 轮。只能靠真实使用校准。
- **临时区什么时候清理**：设计是「落盘或丢弃后即删」，但任务跨很多轮还没被认可时，临时答案会一直挂着。需要一个兜底：M5 结束时必然清理。
- **M4 会不会太晚**：写记忆发生在任务末尾。如果用户中途否定，纠错要等 M4 才写，可能已经忘了细节。
- **场景分支够不够**：code / design / prd 是现在仅有的三个。真实任务常落在缝里（「看看这个设计稿的交互问题」算 design 还是 code）。
- **出口判据会不会太严**：五问里 Q2、Q3 排在最前，意味着大部分东西的正确答案是「不记」。这是有意的，但如果少到「什么都没留下」，记忆就不长了。**这是这一版最大的赌注。**
- **`memory_search` 降级为查找的副作用**：M1 之后 Agent 基本不会主动翻档案。这正是出口理论想要的，但等于承认记录只能靠被追问才用得上。
- **定位层的命名**：代码里仍然是 `features/<project>`，`features` 与「项目」的语义对不上。改名要迁移目录，暂时留着。
